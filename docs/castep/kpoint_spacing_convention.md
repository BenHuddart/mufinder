# K-point spacing convention: findings and open questions

> **Status**: reference note — captures findings from a 2026-05 investigation.
> Three fixes have been merged; open questions are deferred.

---

## Background

MuFinder's convergence sweep reports a "spacing" for each k-point grid in the
log text and in `state.json`.  A bug was discovered and fixed where the reported
spacing was computed with the wrong formula, causing:

1. All grids in the `6×6×5`, `7×7×5`, …, `12×12×5` series to report the
   **same** spacing (0.02005 1/Å) for hexagonal AlF₃, despite very different
   in-plane sampling.
2. Spacings that were approximately **half** the physically correct value.

---

## CASTEP's formula (confirmed from source)

`E:\CASTEP-22.11\Source\Fundamental\cell.f90`, subroutine
`cell_kpoints_spacing_wrapped`, lines ≈ 20765–20773:

```fortran
rx = sqrt(sum(mycell%recip_lattice(1,:)**2))   ! |b₁|, already 2π-scaled (1/Å)
ry = sqrt(sum(mycell%recip_lattice(2,:)**2))
rz = sqrt(sum(mycell%recip_lattice(3,:)**2))
! "add one since mp set is minimum required and int() rounds down"
mp_nx = int(rx / (mp_spacing * two_pi)) + 1
mp_ny = int(ry / (mp_spacing * two_pi)) + 1
mp_nz = int(rz / (mp_spacing * two_pi)) + 1
```

CASTEP's forward direction is therefore:

```
n_i = floor( |b_i| / (s · 2π) ) + 1
```

where `|b_i|` includes the 2π factor and `s` is `KPOINT_MP_SPACING` in 1/Å.
This formula is also used by MuFinder's `grid_from_spacing`.

The physical k-point spacing of the resulting grid is:

```
physical spacing = max_i ( |b_i| / (2π · n_i) )
```

---

## The fix: `spacing_from_grid`

`src/mufinder/science/kpoint_grids.py::spacing_from_grid`

| | Old (buggy) formula | New (correct) formula |
|---|---|---|
| Denominator | `N_i − 1` | `N_i` |
| Aggregation over directions | `min` | `max` |

**Old**: `min_i( |b_i| / (2π · (N_i − 1)) )`  
**New**: `max_i( |b_i| / (2π · N_i) )` ← physical k-point separation

The `min` bug caused the c-direction (short reciprocal vector for hexagonal
cells) to dominate, collapsing all anisotropic grids onto the same value.
The `N−1` bug made every spacing roughly half the correct value for small N.

---

## Round-trip analysis: is spacing_from_grid reversible with CASTEP's formula?

For CASTEP to reproduce grid `(N₁, N₂, N₃)` exactly from
`KPOINT_MP_SPACING = s`, the spacing must lie in:

```
( max_i |b_i|/(2π·N_i),  min_i |b_i|/(2π·(N_i−1)) ]
     ↑ new formula (lo, exclusive)    ↑ old formula (hi, inclusive)
```

### AlF₃ hexagonal (a = 4.872 Å, c = 12.466 Å)

| Grid | lo = max/N | hi = min/(N−1) | Valid CASTEP range? |
|---|---|---|---|
| 2×2×2 | 0.11850 | 0.08022 | **empty** (lo > hi) |
| 3×3×3 | 0.07900 | 0.04011 | **empty** |
| 4×4×4 | 0.05925 | 0.02674 | **empty** |
| 5×5×5 | 0.04740 | 0.02005 | **empty** |
| 6×6×5 | 0.03950 | 0.02005 | **empty** |
| 7×7×5 | 0.03386 | 0.02005 | **empty** |
| 12×12×5 | 0.01975 | 0.02005 | **(0.01975, 0.02005]** ✓ |

Ten of eleven non-Gamma grids in the AlF₃ sweep have **empty valid ranges**.
No single `KPOINT_MP_SPACING` value can reproduce those grids in CASTEP — they
are generated by MuFinder's level-by-level sweep which ramps each axis
independently. For isotropic inputs CASTEP would produce something like
4×4×2, 6×6×3, etc. for hexagonal AlF₃.

### LiF cubic (a = 4.0834 Å)

For isotropic cells the valid range is always non-empty:
`(1/(a·N), 1/(a·(N−1))]`.

- **Old formula** gives `hi = 1/(a·(N−1))`, which is inside the range → 6/6
  round-trips with CASTEP ✓
- **New formula** gives `lo = 1/(a·N)`, which is the exclusive lower bound →
  `floor(N) + 1 = N+1` → 1/6 round-trips (only by floating-point accident)

### Conclusion

| Formula | AlF₃ round-trips | LiF cubic round-trips |
|---|---|---|
| Old (`min/(N−1)`) | 1/11 | 6/6 ✓ |
| New (`max/N`) | 0/11 | 1/6 |
| `nextafter(max/N, ∞)` | 1/11 | 4/6 |

The new formula fails the round-trip because `max/N` is at the **exclusive**
lower boundary of CASTEP's valid input range. The old formula happened to be at
the **inclusive** upper boundary, so it round-tripped for isotropic cells — but
only because it was accidentally computing the right boundary for the wrong
physical quantity.

The new formula is nevertheless correct **for its purpose**: displaying the
physical k-point density in the convergence log and plot. MuFinder recommends
grids ("`KPOINT_MP_GRID N₁ N₂ N₃`"), not spacings. The spacing label is
informational; it is not written to any CASTEP input file.

## Impact of the fix on state.json values

For AlF₃ hexagonal with a 3×3×3 grid:

- Old: 0.0401 1/Å (c-direction, N−1 denominator)
- **New**: 0.0790 1/Å (ab-plane, N denominator) ← correct physical spacing

For AlF₃ anisotropic grids:

- Old: 0.02005 1/Å for *all* of 6×6×5, 7×7×5, …, 12×12×5
- **New**: 0.03950, 0.03386, …, 0.01975 1/Å — distinct values that decrease
  monotonically with increasing in-plane density

## Follow-up fixes (also merged)

### Fix 2: `_compute_spacings` — frozen n=1 direction guard

`src/mufinder/app/convergence_examiner.py::ConvergenceExaminerDialog._compute_spacings`

For cells with a very short direct axis in one direction and a very long axis in
another (e.g. a thin slab), the level-by-level sweep can produce grids where
one direction is frozen at `n_i = 1` while the others grow. Once the
`n_i = 1` direction's contribution `|b_i|/(2π)` exceeds those of all other
directions, the spacing reported by `max_i(|b_i|/(2π·N_i))` stops changing —
every subsequent grid shows the same value, creating a non-decreasing series
that misleads the user about convergence.

**Fix**: in `_compute_spacings`, after computing the spacing for a grid, skip
the entry if a frozen n=1 direction achieves the max. The overview log and
convergence plot simply show no spacing annotation for those grids rather than
a misleading constant value.

Condition: `max_i{n_i=1}(|b_i|/(2π)) ≥ spacing × (1 − ε)`.

### Fix 3: stale `point_spacings` in overview snapshots

`src/mufinder/app/main_window.py::MainWindow._validated_kpoint_overview_snapshot`  
`src/mufinder/app/convergence_examiner.py::ConvergenceExaminerDialog.recompute_spacings_in_snapshot`

The convergence overview widget reads `point_spacings` from the snapshot that
was persisted in `state.json` at adopt-time. After a spacing-formula fix,
projects adopted before the fix continued to display old (wrong) spacings in
the overview panel indefinitely, because the persisted snapshot was never
refreshed.

**Fix**: `_validated_kpoint_overview_snapshot` now calls
`ConvergenceExaminerDialog.recompute_spacings_in_snapshot(snapshot,
host.lattice_vectors)` before handing the snapshot to the overview widget.
This always re-derives spacings from the current host structure's reciprocal
lattice, so both old and new projects show correct values on every load.

The recomputation is lightweight (one call to `spacing_from_grid` per grid
point) and happens only when the validated snapshot is about to be displayed.
The persisted state.json is not modified; only the in-memory copy used for
rendering is updated.

## Open questions (deferred)

### 1. Using spacing for cross-system comparability

`KPOINT_MP_SPACING` is attractive when running calculations across multiple
structures with different cell shapes, because it keeps the k-point density
comparable rather than requiring manual grid specification per system. The
round-trip analysis above shows this is non-trivial:

- For isotropic cells, `floor(|b|/(s·2π)) + 1` with the physical spacing `s`
  gives N+1, not N — CASTEP will use a marginally finer grid than the reference.
- For anisotropic cells, no spacing reproduces the MuFinder sweep grid; CASTEP
  with any single spacing will produce a differently-shaped grid.

**Before implementing cross-system spacing input**, the following should be
decided:
- Should MuFinder use `max_i(|b_i|/(2π·N_i))` as the canonical spacing (the
  physical value, one step finer in CASTEP) or
  `min_i(|b_i|/(2π·(N_i−1)))` (the upper-boundary value, reproduced exactly)?
- How should the mismatch between MuFinder sweep grids and CASTEP spacing grids
  be communicated to the user (especially for anisotropic cells)?

### 2. K-point convergence transfer to supercells

MuFinder already has `equivalent_grid_for_supercell` in `kpoint_grids.py`,
which maps a primitive-cell grid to an equivalent supercell grid by scaling
each axis by `|b_i^{super}| / |b_i^{prim}|`. The spacing-based analogy would
be: adopt the primitive-cell spacing and let CASTEP compute the supercell grid
directly from `KPOINT_MP_SPACING`.

Complication: CASTEP's `floor+1` formula means specifying the primitive-cell
physical spacing produces a supercell grid that is one step finer per axis than
the minimum required. Whether this is desirable (conservative) or wasteful
(extra k-points) depends on context.

The round-trip analysis here provides the numerical foundation for reasoning
about these trade-offs in a future session.
